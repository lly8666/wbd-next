## Selected implementation
- Primary intended Linux forwarded IPv4 TCP path: TPROXY -> real kernel client-facing TCP socket using BBR -> existing bidirectional native epoll/splice -> remote TCP socket. This is the architecture to complete and qualify, then default-enable for supported TCP. Keep original NAT selectable for end-to-end semantics, incompatible destinations/configuration, and as baseline. Do not silently replay or switch an accepted stream to NAT. UDP stays NAT; upload CC still belongs to client OS. Outer TCP-like protocol is not a kernel TCP socket and has no BBR.
- Preserve Go cold control, Rust hot path, original wire/FEC/one-shot repair, current TCP socket ownership and no payload user-copy. Do not invent ARQ, ACK gating, extra reliability, custom CC or new wire. Keep CUBIC selectable for experiments and compatibility. No new client proxy protocol.
- Normal server inbox1024 selected; client/Game128 unchanged. Preserve existing fair admission, no further blind queue expansion. ARM primary for Linux performance; x86 supplementary, Windows requires actual Windows.
- Keep queue algorithm and artificial limit separate: uncapped fq diagnostic candidate, not production default yet. Control useful send pacing at the actual weak-leg sending socket where necessary, never use middle-path artificial rate cap as proof of healthy data plane. Origin cap does not cap proxy leg. Outer theoretical budget 600 Mbps per direction, 400ms RTT. Actual per-direction bytes/packets and losses required; peak capacity headroom desirable, not exact 900 delivered gate.
- Existing FEC profiles and Auto policy preserved; fixed test profiles are not optimal-policy or default-selection evidence. Equal FEC config not necessarily equal actual bandwidth or parity realization.
