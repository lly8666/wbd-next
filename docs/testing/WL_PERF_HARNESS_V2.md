# WL performance harness V2 (M0 Windows Go/Rust)

## Current entry
The real test is `.github/workflows/m0-wl-public-normal-full.yml`, signed Windows Npcap/Wintun, original authenticated Go TLS and WSL2 Linux real raw/TUN. V2 uses the existing `tools/m0_wl_public_rate_app.py`, `tools/m0_wl_netem.py`, `tools/m0_wl_public_normal_e2e.py` and the orchestration `tools/m0_wl_perf_v2_ab.py`. Normal/off alone has a same-process Go-steady test-selectable path vs Rust NativeOwner. No mocked carrier, no bypassing original Apply/Stop.

**One dedicated Actions run = one scenario + one measurement job**, B (Rust) then A (Go) on the same `windows-2025` runner, same source and signed drivers, same original Linux peer. No concurrent Go/Rust legs. A's Go steady state is the *still-present code compiled at the current SOURCE*, not a historical precompiled published Go executable. It uses the same DLL for legacy M1/M3; report both actual paths honestly. New binary artifact is separate from the diagnostic results.

## How to run
On a source with the V2 integration, trigger a workflow dispatch with `public_mode=normal`, `run_n0=false`, `perf_scenario_file=scenarios/wl-normal-150m-300ms-0loss-60s.json`, `perf_ab=true`. The workflow may also have a one-off source-tagged push entry `[plan026-ab-150]`. Do not use N0/P200 in the same invocation. The A/B runner handles two independent original TCP/TLS/OS/WAL/Stop sessions, not two simultaneous products. B runs first so a crashing Go baseline cannot prevent measuring Rust; it will still block the second leg if its own owned Stop is not verified.

`scenarios/*.json`: integer duration (10..240 s), warmup (0..30), drain (2..30), supported TUN MTU, seed; two directional sections each contain offered Mbps (0..350), delay ms (0..2000), loss percent (0..60), optional `tc_rate_mbps`, and packet mix array with `udp_payload_bytes` + `packets_weight` (weighted **per packet**, not per byte; sum <= 100). Source-lock full JSON by SHA. Input-to-generator offered Mbps and actual socket sent/first delivered Mbps are distinct. The original N0 and P200 names, thresholds and evidence remain untouched.

## Exact evidence to read
`result/wl-public/wl-ab-v2/leg-A/` and `leg-B/` contain independent Windows/Linux generator results, 1 Hz whole-EXE Windows CPU+RSS/threads, owner log, and pre/after genuine Linux tc qdiscs. `wl-ab-v2/report.json` contains per-leg offered/first delivered/CPU-seconds/GB and the classified A/B outcome. An invalid scenario, missing authenticated Stop, incomplete same-VM telemetry, insufficient offered rate (each direction >=95% of target) or lost counters -> INCONCLUSIVE/FAIL rather than an invented improvement. Per-process CPU includes Go+Rust and kernel charges; named Rust worker CPU excludes unnamed runtime/driver CPU. Approximate 1 Hz process windows are not per-packet or one-way p99.

Default production builds have no per-packet Rust lock timers. The existing opt-in `win_native_lock_profile` samples 1/64 lock attempts on diagnostic source; it does not establish who consumed all CPU. Separate unexplained TCP-like data loss from actual tc drop and generator capacity. Do not split the NativeOwner mutex or change ciphertext/PN without measured evidence.

## Qualification
Code installed != build PASS != real two-OS PASS != 150Mbps sustained offered != 150Mbps first-delivered, and none implies physical-machine PASS. If either leg fails, preserve first error and both independent reports; do not compare a surviving single leg. At capacity limits stop heavier scenes. Original Linux path and fixed/auto/game modes are not modified by this opt-in Normal-only benchmark.

The fast lane skips three source-unchanged compile preflights and the Linux/Windows native rebuild. It still runs cheap schema/assembly tests, verifies the exact artifact's GitHub run repository and source, checks *all* compiled product/ABI and Cargo.lock files are identical between binary SHA and harness HEAD, verifies manifest and binary SHA-256, installs signed Npcap/Wintun and real Ubuntu WSL2, and exercises true original Go TLS **cold control**, Rust Normal/off NativeOwner and owned Stop. **Measured:** Windows offered 149.9599Mbps (1,234,860 packets); Linux first received 135.4067Mbps (1,116,215 packets); missing 118,645 (9.6080%). Linux offered 146.1655Mbps (1,203,614); Windows first received 144.7718Mbps (1,192,026); missing 11,588 (0.9628%). Both actual kernel netem drops=0. Windows sender bins uninterrupted, max 16ms generator loop gap; Linux generator near 94.082% of one core, max 139.824ms loop gap, but this alone cannot explain ~119k first-delivery shortfall.

**Cross-stage Linux Rust evidence from *the same* run's server.log:**
`V4_PUBLIC_RX_CHAIN raw_observed=1132269 raw_tuple=1132181 data_unique=1118872 link_completed=1118872 tun_delivered=1118872 tun_udp=1118858 tun_failed=0 open_invalid=0 replay_duplicate=0`. Independent Linux UDP app uniquely received `1116215`, so only ~2643 packets are unobserved after the Linux Rust TUN UDP delivery. The much larger shortfall is upstream of (or at) the Linux Rust raw RX observation. The Windows NativeOwner counters show `tx_records=1236096`, `npcap_ingress_local_drops=0`; successful Npcap submission does *not* imply delivery into Linux raw socket. Linux inbound IFB qdisc observed `1250530` packets, drops/overlimits/requeues all zero. Those counters include some control/other packets and different session boundaries, so do not subtract them as an exact per-stage conservation; they strongly narrow the investigation to the WSL2 guest's raw socket, receive backlog or underlay intake, not the final UDP test socket.

**Relevant Rust source:** `crates/wbd-platform/src/linux_raw_carrier.rs` `RawRx::open` uses `AF_INET/SOCK_RAW/IPPROTO_TCP`, `SOCK_NONBLOCK` and `SO_BINDTODEVICE`, but does not explicitly enlarge `SO_RCVBUF`. Linux `/proc/net/raw` carries per-inode raw socket receive queue and drop counters, while `/proc/net/udp` carries the specific generator socket's queue/drops. This is now the **first evidence test**. The V2 generator samples both at 1Hz on Linux, also recording guest-global `Udp: RcvbufErrors` from `/proc/net/snmp`, effective `SO_RCVBUF` and guest `rmem_max`. Preserve the scope: raw entries belong to guest-global raw sockets, not to a confirmed Rust PID unless inode ownership is independently shown. Unknown, missing, reset or changed inodes remain `null`, not zero.

**First-change policy:** If raw socket drop delta accounts for missing packets, add appropriately scoped bounded raw RX receive-buffer sizing/pressure to Rust Linux driver, preserving actual kernel readback, memory/Stop limits and real kernel test. If raw socket drops are zero, capture earlier underlay/WSL2 ingress and M1 counts instead. Do not fix by blindly enlarging buffers or changing Rust AEAD/M2 timers. A 60s red result with exact Stop is valid diagnostic evidence, not protocol qualification.

**Fast path actually measured:** same source-pinned artifact restored and SHA checked; 12s cheap preflight + 217s Windows native job, no Windows/Linux rebuild (three preflight compilers and Linux product builder skipped). Previous full source run: three parallel compile gates up to ~135s + ~100s Linux product job + 340s Windows native job. The ~2.5x wall-clock improvement is for this precise workload and hosted runner; signed-driver/WSL2 environment still fresh and real.

## Confirmed Linux raw socket overflow: same-source Rust-only trial (2026-10-28)

**Authoritative current evidence:** [SOURCE775 Linux raw socket drops](../evidence/M0/PLAN026-WL-V2-SOURCE775-LINUX-RAW-SOCKET-DROPS-CONFIRMED.json), [Actions run 40675314979](https://github.com/lly8666/wbd-next/actions/runs/40675314979), original immutable artifact 12810187258 SHA256 `5b110af2d16c62c6dbf770a28718379a445c858da789cab7a3ec3880b3a0d9df`. No Rust product recompile, same compiled SOURCE0543 EXE/DLL/Linux product, signed Windows driver and true WSL2. Rust Normal/off authentic functional both OS and owned Stop PASS, **150Mbps 99.9%-first-delivery throughput qualification FAIL**.

Linux guest `/proc/net/raw` per-inode drops, measured before/after **same 60s+drain and prior to product Stop**: inode `7924` **162,785 drops**, other two raw sockets zero. Linux guest `net.core.rmem_default=212992` B and `rmem_max=4194304` B. Linux source `crates/wbd-platform/src/linux_raw_carrier.rs::ScopedRawIpv4Rx::open` opens `AF_INET/SOCK_RAW/IPPROTO_TCP` and binds `SO_BINDTODEVICE` but **does not set `SO_RCVBUF`**. Thus Linux guest raw-socket kernel receive overflow is confirmed as a major loss source. Do not infer inode-to-PID identity without `/proc/<pid>/fd` corroboration, or treat all missing app packets as attributable solely to this socket.

Window: Windows sender **1,231,475 packets /149.5494Mbps**, Linux UDP app first received **1,055,855 /127.9407Mbps** (175,620 app-missing). Linux native Rust `raw_observed=1068993`, `data_unique=1057272`, `tun_udp=1057257`, so TUN UDP→Linux UDP receiver difference only **1,402**. Linux UDP **own** socket drops were **308** (`/proc/net/udp` exact inode and guest-global Udp RcvbufErrors agree), not 162,785. Linux inbound IFB qdisc observed **1,231,670** packets but netem dropped **0**. This is an *upstream Linux raw-socket intake* bottleneck, not primarily Python application loss, not TC impairment, and not proven AEAD rejection (`open_invalid=0`). Linux generator offered only 141.6188Mbps reverse and used 61.0658 CPU seconds/65s, so both directions' absolute capacity remains unqualified. UDP RTT p99 rose to ~1252–1313ms from baseline 600ms, indicating queueing but not synchronized one-way delay.

**Narrow next Rust product modification (not part of this fixture/evidence commit):** set an explicitly bounded receive buffer **only** when creating the authenticated Linux raw RX socket; validate `getsockopt(SO_RCVBUF)` **effective** kernel size, budget memory and Stop ownership, preserve BPF exact-tuple and untrusted ciphertext path. This guest has rmem_max4MiB and default212,992B. A requested 3MiB raw `SO_RCVBUF` ordinarily yields up to 6MiB effective (Linux doubles the request), but kernel caps / ownership must be read back; do not claim actual until verified. Rebuild the Linux Rust product once when changed, then source-lock its new SHA and reuse binary for traffic-only trials. Judge against the **same 150Mbps/300ms/0%/60s/99.9%** gate. The earlier Linux TCP harness `ef6bbe9042af197c0c6e9e20d6022b14b69d345a` required both buffer request and effective readback—use the technique, not the previous TCP results as a raw-socket PASS.
