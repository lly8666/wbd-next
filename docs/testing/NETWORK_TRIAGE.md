# 网络测试优化：低成本定位与按问题接班

这是网络矩阵的操作手册，不发布新任务、不取代registry/cursor；场景、指标和当前决策读 [NETWORK_MATRIX_20261022](NETWORK_MATRIX_20261022.md)。本手册规定待实现/接线的监测能力，不宣称全部已经具备。

## 1. 谁推进、先读什么

测试阶段沿用M0作为单一主线写作者和修复集成者；不新增工位，也不要求原聊天一直保留全部记忆。独立Actions并发，不等于几个agent同时改main。确有可分离模块修复时，按现有registry向原工位发一次完整工作包，M0继续无冲突的测试/修复。

全新M0仍按START_HERE恢复，但只保留热上下文：

1. AGENTS与章程中的目标、硬门；main registry中M0及当前有关作者的权限/任务，不全文复述所有工位历史。
2. main真实M0 cursor：当前任务、checkpoint、最后测试源码、一个next_action；检查checkpoint之后的提交。
3. 当前未结束intent和Actions结果；先补遗漏，不重复dispatch。
4. 当前矩阵场景、验收允许带、本手册的对应诊断行。其他架构在问题出现后读取。

沿用治理热读取≤8文件/32KiB上限，不把它当“必须装满”。建议cursor约2~3KiB；完整矩阵、架构和模型按小节检索，不复制到启动提示词。旧代码/协议参考、所有运行日志和历史讨论默认不入热上下文。

同一个角色同时只允许一个主线写作者。全新聊天接任不重置epoch、不伪造已完成、不覆盖旧作者尚未提交的文件。旧作者正常结束前整理在途run与下一动作；意外中断则接班者从提交、workflow/run/artifact事实重建recovered日志，不能猜旧作者意图。

## 2. 最小监测面：优先导出现有字段

基础快照统一包含schema、producer版本、产品SOURCE/build、进程实例、方向、lane/逻辑tunnel的非机密标识、generation、快照序号、单调时间和计数起点。字段分别标available/unknown/not-supported及原因；零是实际零，不能用零代替缺测。进程重启、换代、溢出/重置需要新起点，不能相减成负drop。不要每秒重复完整配置，仅附revision并引用开始时的effective配置。

| 边界/模块 | 最少观测 | 回答的问题 |
|---|---|---|
| 应用生成器与接收器 | 实际发入/首到包与字节、缺失/迟到、发送lag、TCP背压、10ms首到桶 | 是没发够、没到、还是到了太晚？ |
| TUN/Wintun读入 | accepted/rejected及原因、读批次/包数、ready至消费抽样年龄、最后有效读 | 数据是否进入产品？驱动或唤醒是否拖延？ |
| 源队列与调度 | 入/出/明确丢弃、当前/峰值包和字节、最老ready年龄、batch尺寸、预算yield/空转 | 新包被排队、锁、辅助任务还是忙轮询拖住？ |
| FEC组和辅助任务 | class、full/partial、k/r_planned/r_sent分布、组关闭年龄、repair就绪至发送年龄、expired/pressure、decode尝试/恢复/失败 | 保护不足、parity没及时发，还是解码计算/状态出问题？ |
| AEAD/封装 | seal/open成功拒绝、抽样服务耗时、已知复制/临时分配计数（已有则导出） | 计算慢还是适配桥额外复制？不逐包追踪分配器 |
| 外层发出 | 首发/修复/控制各自包与字节、definite/uncertain/not-sent、syscall次数/批量、backpressure | 用户态完成是否真正交给内核？是否因重传挤占？ |
| 外层收到/认证 | raw收到、tuple/长度/校验拒绝、认证拒绝、合法唯一record/重复、最后有效接收 | 网络没送来，还是本地收了但丢在校验阶段？ |
| 解码/LINK/去重/写回 | systematic/恢复首到、重组等待/过期、Game重复、完整packet候选、TUN写成功/失败及年龄 | 合法业务停在FEC、重组，还是系统写入？ |
| M2修复与反馈 | 确认首发F、charged/reserved/accepted/uncertain/refunded R、额度/epoch、缓存数量字节年龄、evicted/expired、候选/发送/拒绝原因、反馈覆盖新鲜度 | 10%是否生效、是否缓存不够、为什么没有修复？ |
| lifecycle/auto | 事件时间、旧/新generation、requested/applied revision、lane active/retiring、payload last-active与control last-active分别记、wake/idle/Stop原因 | 断流来自换代、黑洞、误判idle还是控制器？ |
| 宿主/系统 | 进程及热点线程CPU、RSS、quota/steal/PSI、精确socket/接口drop和队列、注入器成本 | 本机容量还是产品处理能力？ |

已有FEC `ClassStats/OwnerReport`、M2 budget和Windows每秒packet stats先接出。修复“有用/多余”若现有同PN重复无法可靠归因，应报告bounds/censored；不能为了漂亮比例杜撰首发丢失。未ACK年龄表示网络flight或反馈迟到，**不是ready发送队列等待时间**。FEC组形成时间、parity待发年龄、内核传播延迟也分别计，不能混成一条“队列很长”。

计数收支只在同单位/同身份范围内比较：`进入=完成+明确丢弃+在途变化`。FEC、Game和LINK分片有1对多/多对1，必须注明logical packet/source symbol/record/carrier/IP packet，不直接相减。syscall accepted不等于远端交付；最后交付由真实应用确认。保持原本业务标识，不额外向wire插诊断字段。

两端各自单调时钟只能在同内核或已有校准条件下比较。跨机用RTT、各自队列年龄/事件顺序及逻辑计数，不能靠墙钟毫秒对齐来断言谁先卡住。报告snapshot覆盖范围和采集抖动，1秒采样不能证明10ms级因果顺序。

### 采集成本与故障短时取证

- 常态在owner本地累加计数，每秒最多一次快照，诊断默认关闭；不逐包JSON/日志/全局统计锁。输出慢时丢诊断快照并计数，不阻塞业务。统计输出不发入隧道，不刷新payload idle。
- 包龄优先复用已有时间戳；处理耗时用固定空间直方图与抽样，初值1/256加随机采样相位，样本数与覆盖单列。采样不足时p99记低置信，不把少数样本最大值称全量最坏值。服务耗时、队列驻留、线程CPU分开，批处理总耗时不冒充单包耗时。
- 可选诊断级保留最近约5s的100ms计数/队列快照环，进程总上限256KiB；只在有输入的异常阶段输出。没有真实payload、正在预声明黑洞或传播等待时，不因无交付触发“软件死锁”。不得增加逐包全局跟踪表或正文持久化。
- 需要区分CPU热点与锁/系统调用等待时，只开一次5~10s有界profile；Linux perf或Windows已有可用采样工具均可。无权限就NOT_AVAILABLE并用已有计数/线程栈缩小范围，别为了安装大套监控耗费整轮开发。
- 同job同源码同负载比较基础监测开/关或变更前/后一次。目标额外CPU约≤2%、无可分辨尾延迟恶化，这是调查线而非跨机器硬百分比。噪声更大就报无法分辨，不刷重复。诊断ON样本不作为默认性能资格；修复后回到默认状态复验。

功能验收一次批量完成：已知计数输入/输出、一次明确丢弃、一次FEC恢复、一次过期、一次重传预算拒绝、换代reset/Stop以及缺字段处理，验证字段来自真实路径；不能靠测试进程直接填统计对象。增加这些监测不要求另造逐项审批或逐字段Action。

## 3. 用最少实验区分问题

先排来源/输入错误，然后找**最早出现额外等待的边界**；最终掉包处通常不等于根因。相关性用于提出假设，至少一个可区分的反例/干预才支持根因结论。

| 现象组合 | 优先假设 | 下一步仅补这一项 |
|---|---|---|
| UDP实际注入不足，注入器CPU/lag高 | 生成器或host容量 | 同host同包长/PPS直接链路短对照；不要先改协议 |
| 产品前边界持续进、后边界慢，队列年龄增长且某线程CPU满 | 软件热路径计算/调度 | 看该线程一次有界profile，定位复制/编码/遍历，而非扩大buffer |
| 队列长但处理线程CPU低，等待耗时/锁持有高 | 锁跨I/O、唤醒遗漏、反向共锁 | 只看相关等待栈和一次双向/单向差异，不先降FEC |
| 内核收件箱开始掉包，先前产品接收间隔已增长 | 消费者处理不足或调度饥饿 | 对齐raw收→认证→decode→TUN写的队列/进展；不直接增socketbuffer |
| raw收包本来就少，预定损伤匹配，无本地drop | 线路损伤或发送端问题 | 用另一端accepted/接口发出计数及同方向trace界定；不宣布网卡肯定没发 |
| source及时，partial多或r_sent少/过期多 | 组形成/辅助调度不足 | 代入实际k/r与就绪年龄；先调关闭/服务预算，不直接加高档 |
| 理论可恢复的组符号已到齐但未交付 | codec/身份/退役/重组正确性 | 用真实失败元数据生成有界确定性反例；保留独立后续包验证无HOL |
| off缺包多且repair少，expiry/eviction/unknown覆盖高 | 缓存寿命、ACK成熟度或预算 | 按候选→拒绝原因→发送分账复习M2；不能简单移除预算 |
| Game多lane总CPU/等待陡增，单lane健康 | 全局锁、重复处理或跨lane串行 | 单job一项有区分力的lane共享路径采样；按logical字节归一化 |
| 只有内层TCP慢，独立UDP仍及时 | TCP自身恢复/窗口/拥塞 | 看实际TCP窗口、RetransSegs、各流完成CDF；不能直接判隧道全局HOL |
| 换代/idle附近断流或再无唤醒 | 状态迁移/活动定义/旧generation事件 | 对齐生命周期原因与真实payload事件，复习状态机，不靠无限延长timeout |

步骤：

1. 固定source、artifact、请求和失败时间窗，核effective模式/MTU/损伤/负载口径。保留原FAIL。确认是业务目标未达、缺测、夹具故障还是硬门问题。
2. 选上表一行，只提出能被下一份观测推翻的假设；拿已有计数先缩小范围，不先改代码碰运气。
3. 最小重现仍保留触发条件，如双向、实际PPS、混合包、FEC持续满载或换代。不能把持续压力改成串行一包回显再说问题已修。
4. 按第4节复习后修改，一次只改变相关机制；先编译一次，复用产物。一个准确失败反例+受影响功能批次+一个默认诊断状态下同机性能锚点，足以决定是否返回矩阵。
5. 两次同类失败没有新信息，停止重复dispatch和加压，保留OPEN并换一项更有区分力的观测/向独立模块派完整包。无关已可测工况继续；完整性/共享生命周期硬缺陷影响的模式暂停资格扩展。不能为了关闭任务放宽硬门或将OPEN写成PASS。

## 4. 修复前必须定向复习

这是强制的工程步骤，**不需要再请用户批准**。先读现行约束与真实调用链，再看历史原因；旧文档与用户最新授权冲突时按新授权，但必须记录为何变更。

每次实际修复在已有devlog用一个短段落写明：`现象/证据 → 复习的源码与设计引用 → 最近相关修复/未解风险 → 本次改变及保持的约束 → 能区分新旧的回归`。只记可检查的结论，不写长篇推理或复制整个模块历史。文档只读到标题、不读实现不算完成复习。

| 涉及问题 | 按需读的现行设计 | 真实实现入口示例（须核当前调用链） |
|---|---|---|
| 调度/双向锁/内存 | modules/02-RUNTIME、03-MEMORY、04-CARRIER-IO | engine/runtime、memory、platform及当前Linux/Windows packet pump |
| 加密/复制/record | modules/05-RECORD-CRYPTO、01-CONTROL-BRIDGE | codec/record、owner_crypto、实际Go↔Rust桥 |
| MTU/分片 | modules/06-LINK-MTU | FrameBudget、LINK reassembly、实际接口MTU/readback |
| FEC短组/恢复 | FEC_V2_BALANCED当前相关节、modules/07-FEC | codec FEC2、runtime/fec2_owner、生产组合路径 |
| 重传/反馈/预算 | modules/08-RECOVERY | recovery receipt/shadow/budget、实际驱动settlement |
| Game | modules/09-PIPELINE-GAME及当前FEC联合恢复约定 | game_shared、GameAdapter、每lane实际driver |
| 自动档/休眠/换代 | modules/10-LIFECYCLE-QUALITY、当前用户矩阵 | 真实Go控制器、revision/活动计数/Stop，非旧测试helper |

这些路径相对 `docs/architecture/`。先 `rg` 精确符号和决策，再读相关函数及调用者；用 `git log -n 5 -- <相关文件>`/必要的blame找到最近改变，按问题读一两份关联devlog/evidence。若最近提交无关就顺着具体符号追溯，不递归加载整个历史目录。组件实现存在不代表产品已调用，必须追到真实入口。

重点避免回退已验证行为：源不等旧缺口、固定密文重传、放弃不是ACK、owner缓冲不能被复用、正常包不等FEC、Game首到去重、MTU不重复扣除、keepalive不刷新payload idle。不能为“像普通TCP”恢复有序等待，不能因旧参数/Go格式熟悉而恢复已经取消的兼容成本。

## 5. 进度留痕与长期接班

继续使用现有四层：registry发布包；决策/矩阵描述目标；cursor保存当前事实与下一动作；devlog/evidence存证据。不要再加一套测试STATUS、每日无限日报或每bug一份长期启动提示词。

M0发布测试优化阶段时，一次把goal/context_refs指向矩阵与本手册，任务包包含监测接线、有限矩阵、诊断修复和必要复验。当前Windows代码/在途run先结算，不突然改别人权限或将缺线宣布完成。后续已分配包内无需每个run重新请示。共享修改由M0负责，模块工位只在明确边界内自主修复。

cursor热摘要保留：当前正在处理的问题/场景族、产品及夹具来源指针、最重要未关闭风险、在途请求指针和一个next_action。不要复制37行矩阵、几十个run全hash或所有旧S/H到每个字段。每次dispatch前先写现有intent并查是否已有run；结束后一次结果S和cursor H结算一批，不为轮询没变化制造提交。

每个完整场景族、约20~30个实质变更或接近热上下文上限时整理：保留当前结论和未解决问题的引用，旧细节留原路径/commit和历史索引，不删除失败，不迁移原证据造成链接失效。已完成请求按已有归档机制处理；一次整理不是逐文件重写全部治理。

若发现新HEAD与cursor不一致，精确读取增量提交和在途Actions，先补recovered记录。源码变化不自动取消冻结来源的测试；新修复只重跑受影响组，旧SOURCE证据保留原资格。接班没有变化时直接继续next_action，不重新从基础一包测起。

完成本阶段的条件：必要监测真实可用，用户核心场景有可解释结论，已定位硬问题已修或明确阻塞，容量不足项有证据且未冒充PASS，默认性能无已知实质退化；剩余OPEN/NOT_RUN清楚。不是让每个模型预测都精确命中，也不是所有平台全矩阵绿色才允许交付阶段结果。
