# W19 独立单向出口中断根因：IPv4 NUD/ARP 在 netem 仿真 WAN 上重试

对照原生 100Mbps/方向 Fixed Maximum FEC profile6, outer repair OFF, IID30%, 300ms 单程，W19 [Action 40100361068](https://github.com/lly8666/wbd-next/actions/runs/40100361068)，result artifact12562403617，SHA256 `9cb236679011941a276868905936ab5915e42c401397ce37a402a03938c115de`；source `6b08527dbb0af8a626760ff83abcd06de1d42d87`，已冻原生 ARM64 `12562092730`。W19 C→S delivered99.9646Mbps, S→C delivered仅**87.7461Mbps**，S→C missing**36083**，失败真实存在，不能按测量时段成功而改写。Both RX FEC decoder/capacity rejected0, source TUN losses0; client/server product-owned **wbntun0 fq maxrate600Mbit flow_limit256** 和有效 recv/send buffers一致，native M4 source/parity copied; outer DATA修复OFF，两端0次。

**精确 500ms 内核数值断点：** 在 W19 egress-trace 原样数值采样时，相对于首样本 T54.0秒服务端邻居状态 `INCOMPLETE`，T54.5s veth仍发送1441包（过渡）；**T55.0、55.5、56.0、56.5、57.0秒五个间隔其服务端外层 veth TX增加0、netem发送增加0**，但源 TUN每500ms继续增加约4917–4934包，S2C实际应用收不到；邻居项的 probe count在4→5→6间增长。T57.5邻居由 `INCOMPLETE` 恢复 `REACHABLE`，此时出口仅1包，T58.0s后veth TX增3796包、T58.5恢复约7952/500ms。客户端同期间邻居维持 REACHABLE，veth持续正常约7900包/500ms。W18前次 warmup 3.5s仍有M4 source/parity copy，但外层 veth 几乎为0；W16 1.6s C2S outage亦高度一致，尚不能断言每次都为同一ARP事件。

**边界解释：** `fq600` 在**源TUN wbntun0**（内层IP，NOARP），本次中断TUN来源未停；断在实际使用IPv4邻居解析的外层 veth **内核发送M4完成之后、实际到达 tc netem 之前**。一对固定MAC的 netns veth之间不需要动态ARP解析；向 root qdisc `netem loss random 30%` 注入的真实阻断也损伤 ARP探测，使邻居NUD异步陷入INCOMPLETE。这不是原生RS恢复、RX 640容量或CPU满载可解释的。

**最小修复范围：** 新增只允许 `network.owned_veth_static_neighbour=true` 的实验配置开关，默认仍 false。仅在此测试创建的两个临时 netns/两端直接相连veth上，读取对端真实MAC、安装对向 `ip neigh replace PEER lladdr PEER_MAC dev wbn?0 nud permanent`，立即 readback 双向 `PERMANENT` 且对端MAC一致，否则 fail closed；在netem设置30%真实丢包/300ms之前操作。**不修改**任何公用网络岗位的生产 ARP、内核参数、FEC编解码、原生M4、outer重传、TLS身份、产品fq600或虚拟接口限速；不绕过 netem(DATA/Parity仍真正随机丢30%)。500ms只读NUD有效性和veth发包日志属于 opt-in debug。已编写 W20 原案例同固定原生ARM64二进制测试，成功标准：两方向邻居保持PERMANENT，TUN读取/M4复制/netem出口持续，无2+秒黑洞，双向业务损失<=1%，CPU/RSS和真实总外层字节不能劣化；成功后用同样开关但不开重采样单独W21原100Mbps复核。若失败则继续细分 kernel route/netfilter/neighbor，绝不靠刷种子报绿；125–350继续停止。
