## Correct 80Mbps capacity math

Original per-direction offered UDP body size weighted distribution is 64:6,96:8,160:10,255:8,256:6,257:7,512:10,900:15,1287:30 (100 weights). Weighted mean **653.57B**; 80Mbps = 10MB/s => **15,301 original source packets/s**. W126 measured fixed6 source/parity ratio **2.268×**, giving approximately **34,699 independently scheduled Game logical symbols/s** at 80Mbps. Every one is duplicated along Game4 physical ranks due at T0, +4, +20, +60ms. With existing +5ms after-due allowance, **65ms × 34,699/s ≈ 2,255 retained logical jobs**. Current Game4 4096 logical jobs and 4096 FIFO refs PER physical lane yield **only 1.82× slot headroom**, not the incorrectly source-only 4.12×. Real `k/r`, frame-size mix, network packet overhead, slow syscall/PPS and scheduler jitter can increase this; do not guarantee 80Mbps from a static slot count.

Game4 current `GameTx`: 4096 slots, 4096 per-lane FIFO, 8MiB shared logical-byte budget, up-to4096 × 2048-byte source slabs plus arena overhead (configured 16MiB memory cap), RX logical dedup window65536bits. Held common-byte approximation 80Mbps source10MB/s ×2.268 parity factor ×65ms ≈1.47MB only with equal average source/parity sizes. **Actual symbol sizes and slab quantization vary**; use native maximum slot usage, byte high water and abandoned-by-position counters to distinguish byte cap from slot cap. No global queue scans/per-packet timer.

For **100% 64-byte all-small input at80Mbps**, source156,250pps ×2.268 ×65ms≈23,030 retained logical jobs, far above4096; NO qualification. For declared weighted sample, 4-lane physical copy/kernel-send target ≈**138,800 sends/sec per transmitting endpoint** (34,699×4) plus outer feedback; each receiver processes the loss-surviving subset and separately validates original AEAD/PN and shared FEC. Hardware, netem and outer link headroom must exceed sum of actual source+parity×copies, not the nominal 80Mbps application rate. The 300Mbps outer lane shapers used in W125–127 do not prove physical 80Mbps viability.

**Game2 current source** keeps legacy 128 GameTx jobs, 64 FIFO per lane and arena256 source slabs because it has no intentional +60ms scheduled wait. At80Mbps weighted fixed6 34,699 logical symbols/s, a hypothetical **5ms TX owner service delay** alone buffers ≈174 symbols (already >128); 4× short burst allowance ≈694 symbols. **Design candidate** after CPU headroom (NOT committed): bounded 1024 Game2 jobs / 1024 per-lane FIFO / matching arena slab capacity and ≥2MiB logical byte guard, subject to native benchmark and checked source-first preference. Do not silently enlarge old per-lane grace/receiver waiting. An 80Mbps all-64B workload would need a separate much larger budget; fail/stress-stop rather than pretend it is covered.

**FEC encoder** currently has Game pending_jobs64, pending_bytes2MiB, source_arena128 and 5ms closed-job expiry. It accepts fresh sources without waiting but a 20/30Mbps schedule may be CPU-bound before hitting encoder depth. At80Mbps 15.3k input/s and <=12ms Game block close span can temporarily retain up to~184 sources even without parity; **source_arena128 may become the next capacity knee**, but FEC classes close independently and this is only a conservative bound. Design candidate: independent source-arena256–512, pending queue128 (only if measured pressure), no change to 5ms codec expiry without timely-erasure proof; record exact pressure_classes, parity r_planned/r_sent, native copy vs kernel send, and genuine TUN residual for each conditional change.

**Shared receiver**: 4 raw lanes with original separate crypto authentication but ONE shared Game FEC decoder/commit owner. Maintain authenticate→duplicate precheck→decode/recovery→actual TUN write→commit, with only bounded memory/replay. Game4 RX logical dedup65536bits (~8KiB), Game2 current4096bits: required position displacement depends on symbol PPS × (copy lag+path skew+bounded scheduling), not full common RTT. At80Mbps Game4 conservative65ms displacement≈2255 symbols, so65536 ample (subject to class skew); Game2 4096 bit window at current immediate copies covers ≈118ms of 34.7k IDs/s, but true relative skew may be different. Retest native first-delivery/concurrent duplicate/TUN-failure contracts for any RX restructuring.

**CPU core-equivalent floor if costs scaled linearly**: W126 client 50s representative Game TX13.24 CPU-s, four RX15.10, Go and other10.97. At80Mbps 4×=~53/60/44 CPU-s **per same 50s**, or total~157 CPU-s/50s (~3.14 fully loaded cores *per endpoint*, excluding control/harness/kernel interference). This is NOT a reliable throughput forecast or a promise about host CPU count, but shows why a saturated public runner cannot test 80Mbps responsibly. Need demonstrate spare host PSI, real native worker CPU and line/delivery resources before next +10Mbps rung.

## First bottleneck diagnostic gates and escalation rule

1. Authenticate source build and exact public Go TLS/Game4 default/fixed6/native policy; stop if incorrect.
2. Check offered vs sent/received UDP per original packet and per direction; source TUN/root fq drops=0; all-offered deadline delivery, independent small UDP cohort.
3. Inspect FEC source retained/expired pressure and per-class `r_planned==r_sent` (not native candidate=real TUN recovery); Game4 four position `scheduled/sent/abandoned` and due lateness; Game2 lane queue per-lane drops; source slab/byte pressure; raw M4 send failures.
4. Observe RX codec/owner slot/AEAD distinct counters, TUN post-write-only successful dedup, per-TID TX/RX/Go CPU-s, total CPU-s/GiB, RSS and host CPU PSI, vm netem actual line loss separately.
5. **STOP on business failure, admission pressure, netem unplanned shaping or host contention**; do not increase load or rerun seeds to find a lucky pass. Game4 20Mbps and Game2 30Mbps previous original-source host PSI already trigger STOP on current hosted ARM64 VM.
6. First safe W128 performance comparison is one same-VM **10Mbps/dir** Game4 fixed6 IID30 old/new hotpath CPU-only A/B, Action planned from exact new native build. No high-bandwidth promotion until measurable margin restored, and no claim that W128 can eliminate RX/Go CPU without measurement.

## Important corrected historical claim

Earlier [Game4 default integration devlog](../../devlog/fec-network-work/20261026-Game4-default-fixed6-Game2-Game4-IID30-20-to-80-capacity.md) described ~995 concurrent Game4 jobs and ~4× 4096-slot margin by counting **original source packets only**. That was a useful source-only memory estimate but **incorrect for Game4 fixed6 copy scheduling**, which also retains parity symbols in the +60ms queue. The parity-inclusive ~2255 jobs/~1.82× is the actual prudent design sizing at this exact observed k/r mix. Neither is measured 80Mbps capacity. Keep historical text as an explicitly superseded assumption rather than silently deleting the old reasoning.
