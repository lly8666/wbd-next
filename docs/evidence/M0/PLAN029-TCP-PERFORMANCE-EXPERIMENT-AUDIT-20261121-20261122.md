## 0. 使用规则、直接性过滤与术语

- **实验范围**：TCP 传输效率、窗口、内核拥塞算法、吞吐、FEC/机会式修复、TX 批次、qdisc、队列公平、TCP 小流尾延迟，以及足以影响上述判断的诊断与失败。覆盖 **单 ARM/x86 runner 的三个原生 netns**、**单个双端/Windows 验证**、**每组 Windows2025 客户端＋独立 ARM64 中继＋独立 ARM64 接收服务器的两组 3-runner**。区分原始 WBD 产品链路（Windows 签名 Wintun 0.14.1/Npcap 1.88、Go 标准 TLS、Rust native、ARM Rust AF_PACKET/TUN）和 **裸 OS TCP**（只走 Windows Winsock/ARM 内核转发与 TCP，**无 WBD Go/TLS/Rust/Wintun/Npcap**）。两种数据不得混作产品 A/B。
- **联网过滤**：只列有实际 public endpoint `via IP:port`／`DIRECT_CANDIDATE` 的 Tailscale 对端及原生本地 netns；**确认 DERP、无法直连的组从性能结论排除**。例如 [H2302 44978797691](https://github.com/lly8666/wbd-next/actions/runs/44978797691) 原始客户端状态 `INFRA_DERP_BEFORE_EXPENSIVE_PRODUCT_START`，不计入窗口/吞吐对照。`DIRECT_CANDIDATE` **不等于** WAN 已达到 800Mbps，也不等于独立实测的物理直连资格：容量不足另列「环境未资格」，不把其吞吐归咎 WBD。凡只有 Tailscale 状态不明确者不做具体性能结论。
- **真实 `success`**：必须实际执行 native job、源锁、产品/OS TCP、远端接收、Stop；`static=success` 而 native=`skipped` 是「**假绿：未执行**」。**Action 红**分为①`REPORT/ASSERT FALSE RED`（被确证的业务阶段完成，后置报告器/测试附属断言失败）；②`PARTIAL`（确有已完成腿，但其他腿未达门）；③`TRUE DATA/RECEIPT FAIL`（真实 bulk 未完整交付、ACK/EOF 超时）；④`PREFLIGHT/INFRA`（无有效受测业务）。不因任务红就丢弃已完成腿，也不把局部 PASS 改称整体 PASS。后置测试 keeper Stop 不等于产品 owned Stop；两者分别记录。
- **`BBT` 理解为 BBR/BBR2（如用户所指为另一算法，原证据未出现）**。`CC=未验证` 不等于 CUBIC、也**不等于 BBR**。显式 `BBR2` 指 **Windows 的 TCP CongestionProvider 模板**；Linux 旧 `bbr` 是不同实现。`Get-NetTCPConnection AppliedSetting=0` 是数值枚举 **Internet**，不等于「没有应用」；模板已修改 ≠ 独立证明实际 Socket 算法每个时刻的内部状态。
- **窗口量纲**：`SO_SNDBUF/SO_RCVBUF` 为实际 Socket 缓冲容量，`SndWnd` 为对端通告的发送窗口，`Cwnd` 为本机内核 TCP 拥塞窗口，`BytesInFlight` 是在途未确认字节，`MSS` 为 TCP payload 分段大小；它们**不能互相代替**。TCP-like 外层 FakeTCP window / ACK / SACK 并非内层 Windows TCP cwnd。`ss cwnd=10` 若来自 ARM 接收服务器，代表 **ARM 作为发送方** 的 cwnd，不可冒充 Windows 发送端。
- **负载/度量**：通常 4 条真实 TCP bulk 在各自 25s offer 窗发送，另 160 稀疏 TCP echo（Linux 单 runner 还含 160 UDP）；三 runner 业务完整常按接收端 exact 8-byte receipt/FIN 来判定。以接收端唯一有效字节及本机 A→B→A′ 为基准，`sendall()` 完毕**不代表**接收完成；成功的 160/160 echo **不代表** bulk 成功或 P99 达标。不同 runner 绝对 Mbps 不做跨机因果差值。

## 5. 结论与下一轮最小可区分测试（不改变产品红线）

1. **0% 数据面服务能力**：Windows 同一源码 A/B/A′ TX8/NPF16KiB→TX16/NPF64KiB 的真产品双组是这两天最清晰的正收益（H2292）。但主分支仅保留 opt-in feature **默认 OFF**；还缺 1/5%＋FEC＋模式＋真实物理资格，不能直接默认开启。Linux 单 runner 热点显示 TX/RX 系统态和内核调用墙钟时间较重，但扩大现有 32 条批次不自动有效。
2. **0% RTT400 的裸 TCP 确实会被 Socket Buffer 卡住**：H2282/H2283 几倍至几十倍增益来源于同时改变 Windows/ARM OS 缓冲，不能偷换成 cwnd 优化；H2304 产品 loss0 两档显示效益不稳定、源数据漂移与 CPU/P99 代价；不能推论“越大越好”。
3. **1/5% RTT400 存在独立的 TCP 拥塞与修复问题**：H2309 的真实 Windows TCP_INFO 显示 5% `Cwnd` 小到 5–12KiB，`SndWnd` 仍 ~8.45MiB；H2310 **无 WBD 裸 Windows BBR2**也出现 5%窗口塌缩和 remote receipt 失败。所以**不能将全部失败归咎 WBD，也不能证明 WBD 无额外损耗**。
4. **FEC2 的保护收益是真的，但不能替代可靠 TCP**：H2293 的测试 keeper 清理红不抹去 A/B/A′业务值；H2307 正向与反向 FEC 固定/OFF/固定进一步证实。**无跨业务 HOL、首次独立 DATA 立即交付、原密文最多一次机会式修复、R/F 预算、有界内存及真实 Stop**不变；不能为追吞吐把外层改成新 TCP 栈/持续 PTO。
5. **唯一合理的下一轮高信息量试验**：在经过物理直连、clean relay 可承载门槛的**相同两套三 runner**上，使用同一 sender `MSS/offload/套接字缓冲/Windows CC 实际读回` 与相同 netem qdisc 损伤粒度，顺序执行 **裸 TCP BBR2 ↔ 原产品 Normal/off BBR2 ↔ 裸 TCP BBR2**，分别在 0%、1%、5%（每档单独两组）采 **远端唯一接收 goodput、4流每2s `Cwnd/BytesInFlight/SndWnd/RTT/RTO/BytesRetrans`、Windows内层 ACK、WBD M1/M3/M4 driver accepted prefix 与队列 age、ARM TUN/内核 OOO/SACK**。如果裸、产品同时相似塌窗，优先分析真实 packet-loss/ACK/OS CC；如果产品在等价窗口提前塌，沿第一个额外丢包/排队边界追查。严格记录源 SHA 和每个失败 leg，维护 A→B→A′、原产品 owned Stop。切忌全局强制 Windows BBR2、重启用户机器、改外层拥塞为可靠 TCP 或把假红变假绿。
