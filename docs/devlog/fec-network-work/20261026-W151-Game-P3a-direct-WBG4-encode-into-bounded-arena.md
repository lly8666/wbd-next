## Problem and strictly minimized code

GameAdapter::enqueue (source AND FEC parity symbols) created a new `wbd_codec::encode_game()` heap Vec, then took a preexisting unique 2048B GameTx arena slab and copied the full encoded Game buffer into slab bytes14..; one per-logical-symbol Vec and full buffer copy were redundant. Original source_arena in FEC encoder still deliberately lasts only until encoder closure, and the 60ms pending Game physical-copy jobs must own independent GameTx slabs. Never pin a whole FEC group across staggered physical copies to claim zero-copy.

P3a uses two small changes:
1. `crates/wbd-codec/src/lib.rs::encode_game_into`: explicit exact old `WBG4 + big-endian logical ID + 16-bit len + flags zero + payload` into caller-owned slice after **all bounds validated before any write**. The legacy public `encode_game` API delegates to the same implementation; no magic, flags, version, logical-ID or payload-wire contract changes. Target too small => Truncated; budget too small => BudgetExceeded; invalid u16 len => InvalidLength. New R0 codec golden tests check 0,1,3,16,64,1287,2001B payloads, correct output, untouched tail and no mutation on rejected inputs, original constant golden for 3B.
2. `crates/wbd-engine/src/v4_game_lane.rs::enqueue`: reserve original Game4 capacity first, allocate the **same bounded slab** and call encode_game_into directly at slab[14..], then GameTx.offer with same Mode::Game, length, 31B record overhead and one still-valid logical job per symbol. Does not change GameTx draining, replay, FEC queued rows/credits, stop, generation, TLS or per-lane AEAD. No added queue, timer, thread or second memcpy. No Normal receive/TX data path is modified; codec module is shared but Game-specific API only. Native Normal correctness regressions still must pass, real Normal five-mode qualification remains older exact source until independently run.
