## Problem and strictly scoped implementation

Original Game4 worker waited for TUN readiness or `game4_next_due_ns()` with a 10ms idle poll cap; that tracks 0/4/20/60ms **delayed copies**, but not the existing `Fec2Owner` source group closure. A single sparse fixed6 source group can have its own ~7–8ms closure while the next physical Game4 copy is at 20ms: later parity preparation is an avoidable missed deadline even when CPU is idle. Continuous traffic already advanced FEC in bounded quanta independent of the full60ms copy queue. This is a scheduling correctness improvement to verify separately, **not proven as a CPU bottleneck** and not permission to increase send load.

- `crates/wbd-engine/src/v4_game_fec.rs`: `GameFecTx::next_due_ns(now)` returns immediate for queued repair or next ready SIMD work and otherwise derives the earliest original FEC close/expiry deadline; no new timer, no per-packet heap allocation or lifetime extension.
