## What actually owns the congestion window

- Original Windows signed Wintun carries the app's **real Windows kernel TCP sockets**; original ARM/Linux TUN carries real Linux kernel TCP sockets. WBD original Go FakeTCP/TLS and Rust M1/M3/M4 outer encrypted record presentation are **not** Windows/Linux kernel TCP data sockets. BBR selection on a FakeTCP-looking outer IPv4 header has **zero inherent effect** on inner cwnd/RTO.
- On Windows, Microsoft documents `netsh interface tcp set supplemental template=custom congestionprovider=bbr2` (specific support/readback OS-dependent) and source/dest-port template filters via `tcp add supplementalport`. These are **system TCP template** mutations, not per-WBD-inner-socket APIs. Even setting the Custom template can affect other apps on the same host; use only disposable isolated Windows2025 runner, only after exact baseline profile snapshot, scoped 45902 filter, exact reset of both changed template and filter, and verify local TCP stream actually uses it. On physical user hosts, no blanket BBR2 authorization.
- On Linux, `TCP_CONGESTION` applied by `setsockopt(IPPROTO_TCP)` to a **WBD-owned test TCP client socket or TCP listener** is per-socket and readback verifiable. Passive Linux accepted sockets inherit listener choice; verify after accept. On external app sockets that WBD does not own, the same user-space function cannot override their stack. `tcp_available_congestion_control` and kernel module state are build-specific; `bbr` availability is necessary but not a 3Runner success. `bbr2` is not assumed available in ordinary upstream Linux kernels.
- A congestion algorithm is chosen on the **sender**. For Windows→Linux bulk, Windows Windows TCP sender matters, not just Linux server listener; for Linux→Windows download, the Linux server sender matters. Perform directional and crossed policies without conflation.
