# M0 PLAN026 — prevent Windows WSL2 full-source Actions from swallowing failure/Cancel

2026-10-29. User reported multiple Windows full original Go TLS/Rust/Npcap/Wintun↔WSL2 tests that kept running despite Cancel. Checked exact `main`/cursor and live GitHub jobs: Actions [40859233957](https://github.com/lly8666/wbd-next/actions/runs/40859233957) sourcea8 and [40860233126](https://github.com/lly8666/wbd-next/actions/runs/40860233126) source134 had all compile/Rust/Go jobs SUCCESS but were stuck inside `native-public-two-os → Launch actual WSL2 Linux and direct full public two-OS product`. Both were successfully source-guarded cancelled via a **one-shot** GitHub Actions `actions:write` task [40864409246](https://github.com/lly8666/wbd-next/actions/runs/40864409246), and GitHub now says **completed/cancelled**. The privileged one-shot workflow file was **deleted in the same next batch**. No fake Windows functional PASS for either cancelled run.

Confirmed my previous partial guard was insufficient: workflow `.github/workflows/m0-wl-public-normal-full.yml` still had 40min entire WSL2 test step / 60min job; its Python 165s individual mode timeout ran only AFTER WSL2 download/import/boot, exact-driver firewall/Npcap OS setup, and opening native modes. It therefore could not stop WSL2 setup stalls or an unbounded `wsl.exe` in Python's `finally` teardown. `tools/m0_wl_public_normal_e2e.py::stop_linux()` used `subprocess.run(wsl.exe ... kill ...)` with **no timeout**, meaning one genuine failing mode could appear permanently running during cleanup. The long job is CI orchestration failure, not evidence that established Normal/off Rust product must be rewritten.

Fixes (test/CI only, no product data path):
- New `tools/m0_wl_windows_bounded_cmd.py`: each sensitive original `wsl.exe --list` (30s), official Ubuntu WSL import (180s), guest apt prerequisite (120s), actual Linux iptables/eth0 lookup (25–30s) has independent OS-child tree deadline. Output goes to an OS temporary file instead of PIPE so orphan WSL descendants cannot keep inherited pipe descriptors open and make Python `communicate()` wait forever; timeout kills the external Windows OS command **tree**, prints explicit `WL_WSL2_COMMAND_TIMEOUT`, exits 124. No fabricated success or fallback VM.
- New `tools/m0_wl_windows_step_watchdog.py`, started immediately when the real PowerShell WSL/native full step starts, monitors 1020s **whole step**, and forcibly stops that step's owned Windows process tree if boot/firewall/native WSL/cleanup blocks. Removed via a sentinel and Stop-Process on normal/fail exit; workflow step has additional 24min GitHub ceiling and job 38min. Cleanup steps are scoped separately 2min, Npcap 4min.
- Python real mode batch retains 165s functional timeout (1200s for explicit performance) with recursive Windows taskkill, but now **aborts the entire remaining batch after the first mode timeout**, rather than trapping the runner in six more expensive modes. The concrete timeout remains a FAIL, not an assumed other-mode PASS.
- In the authentic `tools/m0_wl_public_normal_e2e.py`, original-Go server Stop request is still sent but Windows `wsl.exe -- kill` request now has 8s limit and non-PIPE I/O, cannot swallow the genuine preceding failure in `finally`.
- Added offline regression `tests/test_m0_wl_native_os_deadline.py` exercising a genuine child command normal completion and real sleep timeout exit124, checking whole-step and clean Stop guards, plus workflow cheap checks and Python syntax validation. The batch commit includes `[plan026-coding]` so it triggers **cheap preflight** while intentionally skipping another expensive full signed Windows↔WSL2 job until explicitly scheduled after guards green.

All original normal/off signed native functional, Rust-exclusive I/O, authentic TLS/AEAD/PN, original cipher, driver receipts, Stop semantics are unchanged.
