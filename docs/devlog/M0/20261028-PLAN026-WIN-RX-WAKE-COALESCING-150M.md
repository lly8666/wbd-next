Research validated the existing safety/capacity decisions:
- [Npcap developer sendqueue guide](https://npcap.com/guide/npcap-tutorial.html) and [API](https://npcap.com/guide/npcap-api.html): `pcap_sendqueue_transmit` reduces context switches compared with repeated `pcap_sendpacket`; **sync=0** avoids busy-wait timestamp scheduling. Already used correctly in `windows_native_io.rs`; do not remove it.
- [Official Wintun API](https://github.com/WireGuard/wintun/blob/master/api/wintun.h): release each Wintun receive loan through `WintunReleaseReceivePacket` after consumption; sender must use allocate/copy/send. Do not hold borrowed RX pointers across owner lock/driver Stop to “optimize” copy.
- [Microsoft SetEvent documentation](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setevent): auto-reset events hold a signaled state until one thread waits; setting an event already signaled has no further effect. This justifies **merging repeated notifications of authenticated state changes within the already-bounded ready batch**, but does not prove a CPU speedup before an OS test.

## Minimal product change: 32-authenticated-record wake batch, never artificial delay

Only `crates/wbd-engine/src/v4_windows_native_runtime.rs` is changed in product. Old `open_and_deliver` called `tx_notify.wake()` for each valid authenticated DATA or CONTROL record after M3/PN verified and ACK stored; invalid/malformed/replay packets never caused a wake. New `open_and_deliver` returns `Result<bool,i32>`: verified DATA or CONTROL returns true, rejected record false, fatal failure unchanged. RX owns a local non-shared `TxWakeBatch` and calls `SetEvent` **once per 32 verified records** instead of once per record. When NPF returns NoPacket or its existing bounded 32-packet drain ends, **flush the partial group immediately**, never wait for a deadline or future traffic. Real Go→Rust handoff ciphertext retains its original FIFO, and an independently bounded wake group flushes after its complete drain. A single valid DATA or CONTROL thus still wakes TX on same-ready-batch completion. Stop cancellation remains first-priority, failing worker wakes Stop. M2 deadline, original TX 8-record batch / two Entry locks, AEAD/PN uniqueness, NPF Accepted/Uncertain prefix, Wintun lifetime and original Go TLS are unchanged.

Add one-shot `WBD_WINDOWS_RUST_NATIVE_WORKER_TID role=TX|RX tid=<GetCurrentThreadId>` at actual Rust worker start; no packet-path logging or clock. This allows the external 1Hz sampler to join hot threads by OS TID when `GetThreadDescription` is unavailable, rather than assigning unknown Go/Rust threads. The owner logs **at joined Stop** `WBD_WINDOWS_RUST_NATIVE_WAKE_BATCH max_verified_per_wake=32 tx_wake_attempts=N rx_data_delivered=N joined=true`; wake attempt count is incremented **once per actual batch wake**, never once per packet. ACK updates can include CONTROL and handoff, so raw DATA delivery divided by wake attempts is a diagnostic ratio, not an exact 32-per-batch guarantee. Pure Python parser joins unique TX/RX startup markers to real per-thread Win32 kernel/user CPU and fails closed for multiple/ambiguous marker IDs. Rust unit test asserts lone authenticated record is flushed, 32 -> one wake, 33 -> two wakes, and zero records -> zero wakes; Python parser tests reject duplicate TID and missing logs.
