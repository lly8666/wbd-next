## Windows source code-path review and plausible ROI (not measured function CPU)

- **Outbound source:** original Wintun receive `crates/wbd-platform/src/windows_native_io.rs::WintunRx::read` copies one packet to a 2048B reusable owned source slab; 8 packets batched under one Rust `Entry` lock for seal/unique PN `v3_seal_entry`, then `packet_frame` builds TCP/IPv4/Ethernet into separate 2304B slabs, then `NpcapTx::send_batch` copies READY frame bytes into NPF sendqueue, with second shared owner lock for exact M2 Accepted/Uncertain receipt. Max batch8; default NPF sendqueue short commit. Per packet has at least source, frame and queue copies. **Most likely measured costs to look at**: Wintun read syscall/copy, AEAD seal under lock, NPF queue copy + transmit syscall; counts and actual timings not yet attributable.
- **Inbound source:** `NpcapRx::read` calls `pcap_next_ex` per captured frame and copies `caplen` into fixed ~64KiB stack slab; owner checks exact tuple/persona and M3 AEAD/PN under one `Entry` lock, then Wintun allocate/copy/send per authenticated IPv4, and triggers `tx_notify.wake()` **per accepted DATA/CONTROL record**. This wake is a candidate kernel-call overhead/coalescing opportunity, but must first measure and preserve M2 deadline, ACK advancement, Stop and immediate wake behavior before changing.
- **Shared owner:** existing default TX already batches 8 sources into one seal lock + one M2 settlement lock, and `m2_wake_timeout_ms` already uses exact feedback/shadow deadlines instead of fixed20ms polls. Existing `win_native_lock_profile` samples 1/64 mutex entries only in a separately compiled opt-in diagnostic Rust binary; the 150Mbps measured production build has `rust_owner_lock_wait.status=NOT_MEASURED`. A contention claim or splitting owner locks now would be speculative.
- **External Windows Python generator:** separate process CPU **48.3906s/65s** during this workload, and must not be included in the EXE's 14.9375s. Combined power/driver DPC attribution requires ETW, which is NOT present. A 150Mbps app test can PASS without exposing per-function CPU.

**Priority:** (1) fix read-only thread identification and per-TID user/kernel CPU visibility; (2) if kernel-charged worker significant, sample NPF and Wintun call wall duration at low rate / Windows ETW stacks; (3) if user-charged worker significant, sample AEAD/seal/open, parsing and owner lock separately; (4) only after same-source evidence consider copy coalescing or per-batch ACK wake, with dual owned Stop/replay/reorder and 150Mbps performance invariant. Do NOT optimize high-rate benchmark Python generator under the product CPU label.
